# ADR-0019: LLM に渡す会話は直近 6 往復に限る

- ステータス: 採用
- 日付: 2026-10-09

## 背景
会話のチェックポイントは、利用者の発話・AI の返答・ツール結果をすべて保持する([ADR-0006](0006-session-memorysaver.md)、[ADR-0015](0015-shared-postgres-checkpoints.md))。LLM への入力を組み立てる `messages_for_llm` は、ツール結果を直近 1 回分に絞っていた([ADR-0011](0011-three-path-data.md))。一方で、発話と返答は全件を Bedrock に渡していた。上限用の `truncate_messages` は定義だけで、どこからも使われていなかった。

API には認証がなく、`context_id` は利用者が選べる。同じ `context_id` で往復を重ねるだけで 1 回の入力が伸び続けるため、運営者の Bedrock 費用が会話の長さに比例して増えていた。セキュリティ監査(cloudflare/security-audit-skill、quick、2026-10-08)でも、この点が要検証の候補(`shoppie/unbounded-conversation-history-llm-spend`)になった。`.claude/rules/ai-agent-context-engineering.md` も、会話履歴に既定で有効な上限を求めている。

## 決定
`messages_for_llm` で、利用者の発話の数で数えた直近 6 往復だけを LLM に渡す。切るのは往復の境目で、先頭は必ず利用者の発話にする。チェックポイントの保存内容と画面への応答は変えない。上限は定数(`MAX_LLM_HISTORY_TURNS`)で持ち、環境変数で無効にする手段は作らない。

## 理由
- 会話 UI の費用とレイテンシ(Claude Haiku 4.5、`max_tokens=256`)を、会話の長さに依存しない上限に収められる。
- 商品探しの会話で参照されるのは、直前の条件と、直前に出た商品であることが多い。条件の言い直しを含めても、6 往復あれば足りると判断した。
- 往復の境目で切るので、ツール呼び出しと結果の組が途中で切れない。Bedrock が求める「先頭は利用者の発話」も守れる。

## 検討した代替案
| 案 | 良い点 | 見送った理由 |
|---|---|---|
| 既存の `truncate_messages`(文字数から見積もったトークン数で切る) | 入力量を直接抑えられる | 往復の途中で切れ、ツール呼び出しと結果の組や先頭の発話が崩れる。見積もりも文字数 / 4 で粗い |
| 古い往復を要約して残す | 長い会話の条件を保てる | 要約のために LLM 呼び出しが増え、費用とレイテンシが上がる。いまの会話の長さでは不要 |
| 上限を環境変数で変えられるようにする | 本番で調整できる | 0 や大きな値で上限を外せる余地を作らないため、定数にした |

## 影響・見直し条件
- 7 往復以上前の発話は LLM から見えない。早い段階で伝えた条件(予算など)を、後の往復で使えなくなる場合がある。
- 本番で「前に言った条件を忘れる」という反応が増えたら、往復数を見直すか、条件だけを要約して残す方式を検討する。往復ごとの入力トークンは、まだ本番で測っていない。
