# ADR-0014: ユーザーの反応は、往復の識別子に結び付けて構造化ログに記録する

- ステータス: 採用
- 日付: 2026-10-08

## 背景
エージェントの構成(プロンプト・モデル・ツール定義・LLM に渡すフィールド)は、固定した発話と商品によるオフライン評価でしか比べていなかった([T-0003](../trials/0003-KEY-llm-context.md) 回7)。本番で提案した商品が開かれたか、言い直されたか、会話をやめられたかは記録していなかった。

商品の購入はモールのサイトで起きるため、Shoppie から直接見えない。Shoppie 側で取れる反応は、商品カードのクリック・次の発話・会話のリセットに限られる。DB は持たない構成で([ADR-0006](0006-session-memorysaver.md))、ログインもない。

## 決定
- `POST /request-assistance` の応答に `turn_id`(往復ごとの UUID)と `config_version`(構成の識別子)を足す
- `config_version` は、モデル・`temperature`・`max_tokens`・システムプロンプト・ツール定義・LLM に渡すフィールドから作るハッシュ(12 文字)にする。手で版を上げない
- サーバーは往復ごとに `turn_completed`(商品数・モール別の件数・処理時間)か `turn_failed` を記録する
- ブラウザは `POST /events` に `product_click`(表示順・モール・価格)と `conversation_reset` を送る。`sendBeacon` を `text/plain` で使い、サーバーは本文を JSON として読む
- 記録先は標準出力の構造化ログ(`interaction_event {JSON}` の 1 行)にする。Render がデプロイしたコミットも載せる
- 発話の本文はイベントに含めない
- 集計は `fastapi/backend/scripts/aggregate_interaction_events.py` で、ログから構成ごとのクリック率・押さずに次の発話をした率・押さずに終わった率・0 件率・失敗率・リセット率を出す

## 理由
- 往復の識別子と構成の識別子があれば、反応を「どの構成の、どの返答」まで遡れる。クリック率だけを全体で見ても、何を直せばよいか分からない
- 構成の識別子を設定から作ると、プロンプトを変えたのに版を上げ忘れる、ということが起きない
- ログに出すだけなら、外部サービスへの送信・追加の契約・本番の環境変数の追加・DB の新設がいらない。個人開発の運用コストを増やさずに始められる
- 商品カードを押すと別タブでモールに移り、アプリ内ブラウザではページが閉じることもある。`sendBeacon` ならページが閉じても送れる。`text/plain` にすると CORS のプリフライトが起きない
- 発話には個人情報が入りうる。本文を持たなければ、プライバシーポリシーと保持期間の判断を先送りできる

## 検討した代替案
| 案 | 良い点 | 見送った理由 |
|---|---|---|
| GA4 のカスタムイベント | 無料。ファネルの画面がある | 外部サービスに会話の識別子を渡す。プライバシーポリシーへの追記と、測定 ID の本番設定が要る |
| Vercel Web Analytics のカスタムイベント | 導入が最も簡単 | カスタムイベントは有料プランの機能 |
| DB(Cloudflare D1・Supabase など)に保存 | 長く持てて、問い合わせもしやすい | 「DB なし」の判断を変える。まだ件数も分からないうちに入れる理由が弱い |
| 自前のリダイレクト(`/go?url=...`)でクリックを数える | 確実に数えられる | アフィリエイトリンクを書き換えることになり、モールの規約と相性が悪い。遷移も遅くなる |
| `config_version` を手で付ける | 読みやすい名前にできる | 付け忘れると、違う構成の反応が混ざる |

## 影響・見直し条件
- Render のログは保持期間が限られるので、集計するにはログを定期的に書き出す必要がある。書き出しの手間が負担になったら、ログの転送か DB を検討する
- `POST /events` に認証はない。不正な送信で指標が汚れうる。本文の大きさと項目は検証するが、送信数の制限はない
- 発話の本文を持たないので、「押さずに次の発話」が言い直しか正当な絞り込みかは区別できない。外れた往復を分類して評価セットに足す段階([T-0016](../trials/0016-KEY-user-feedback-loop.md))で、発話を保存するかを改めて決める
- `config_version` はハッシュなので、どの変更に当たるかはログの `commit` と合わせて読む
