# ADR-0017: 反応イベントを Supabase の PostgreSQL に保存する

- ステータス: 採用（実装・ローカル検証。本番接続はまだ実施していない）
- 日付: 2026-10-08
- 関連: [T-0016](../trials/0016-KEY-user-feedback-loop.md)、[ADR-0014](0014-interaction-events-log.md)

## 背景

ADR-0014 では反応イベントを構造化ログに記録した。ログ保持期間に依存せず継続してデータを貯めるため、永続的な保存先を追加する。フロントと Python バックエンドは既存の Vercel・Render に置く。

## 決定

Supabase の PostgreSQL に `shoppie_analytics.interaction_events` を作る。`INTERACTION_DATABASE_URL` をバックエンドだけに設定し、Session pooler と TLS を使う。会話履歴の `DATABASE_URL` とは分ける。発話本文・IP アドレスはイベントに保存しない。

ブラウザから DB へ直接書き込まず、既存の `/events` とサーバー側の往復記録を使う。非公開スキーマで RLS を有効にし、ブラウザ向けの権限・ポリシーは作らない。DB オーナー接続が保存する。

保存は上限 1,000 件のキューと別スレッドで行う。同じイベントを標準出力にも記録する。DB が利用できないときはログを残して会話を継続する。設定済みの DB 接続とテーブルは起動時に検査する。環境変数が未設定なら従来のログ記録を使う。

DB から既存ログ形式へエクスポートし、ADR-0014 の集計スクリプトで構成ごとの指標を出す。導入と運用手順は [Supabase の README](../../infra/supabase/README.md)に記載する。

## 理由・代替案

PostgreSQL で保存すると SQL による調査と他の PostgreSQL への移行ができる。Supabase は無料枠から始められ、将来の認証にも利用できる。RDS は今回の小規模な反応収集には固定費が大きく、ログだけでは保持期間と書き出しの手間が残る。

## 限界

キューは永続化しない。強制終了・DB 障害・キュー満杯では DB に保存されないイベントがあるため、ログの回収が必要になる。公開 `/events` の不正送信やブラウザ再送による重複は防いでいない。クリックは購入ではなく、会話終了・言い直しも直接確定できない。

本番の反応指標・Supabase の実使用量はまだ測っていない。無料枠の上限と一時停止、自動バックアップがない点を踏まえて運用する。[Supabase 料金](https://supabase.com/pricing)
