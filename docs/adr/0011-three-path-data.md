# ADR-0011: 画面・LLM・会話チェックポイントに渡すデータを分ける（三経路）

- ステータス: 採用
- 日付: 2026-10-02（記録日。判断はそれ以前。[technical-qa.md](../technical-qa.md)・[langgraph-agent.md](../langgraph-agent.md) から起こした）

## 背景
モール API の生のレスポンスをそのまま LLM に渡すと、入力トークンがすぐ膨らみ、コスト・エラー・遅延が増える。

## 決定
| 経路 | 中身 | 用途 |
|---|---|---|
| MemorySaver | ツール結果のフル JSON | 会話のチェックポイント |
| Bedrock への入力（`messages_for_llm`） | 直近のツール結果の全件。`title`(80文字まで)・`price_yen`・`marketplace` と、元データにある `review_rate`・`review_count`・`shipping`・`condition` | 応答文の生成 |
| API レスポンス | フルの商品データ（件数は絞らない） | 画面の商品カード |

件数を間引くと比較の体験が損なわれるので、件数ではなくフィールドを削る。

変更の経緯: 画面に出す商品は以前「最大 10 件に厳選」していたが、件数制限なしに変えた（`ProductCurationService` は正規化のみ）。
[backend.md](../backend.md)・[architecture.md](../architecture.md) の「最大 10 件」の記述は古い。

### 2026-10-06 の見直し

当初は、商品名・価格・モールを中心とする最小フィールドに絞っていた。同じ100商品・20発話を使った4構成の比較では、レビュー・送料・商品状態を加えた `enriched` が、全フィールドから入力トークンを69.0%減らし、条件内の最安選択に23/38回成功した。実験時の最小フィールドは10/38回、全フィールドは19/38回だった。

この測定済みの `enriched` を暫定標準とする。追加する4フィールドはキーが存在する場合だけ元値をコピーし、`null`・空文字・0も保持する。ツールが返していないレビュー・送料・商品状態を推定して追加しない。URL・画像・説明文は画面の商品カードに渡す。直近のツール実行分の商品件数と順序は保つ。

プロンプトでは、レビュー評価と件数の双方を確認し、条件付き送料無料を通常の送料無料と区別する。共有データで確認できない属性は推定しない。Amazonの検索リンクは `amazon_search_link` で識別し、実商品の0円として比較しない。

5検索・20種類の作成した発話を各2回測った代理評価であり、本番における最適な組み合わせを確定したものではない。80文字への短縮で属性の支持語が失われる例と、説明文にしか支持語がない例があった。タイトル延長や説明文の選択的な共有、数値処理による最安選択は別の検証対象とする。

測定条件・結果は[実験レポート(Markdown)](../reports/20261006_tool-payload.md)・[HTML版](../reports/20261006_tool-payload.html)、適用の記録は[T-0003 回8](../trials/0003-KEY-llm-context.md)に残す。

## 理由
- 「ユーザーに渡すデータ」と「モデルに渡すデータ」を分ければ、表示を削らずにトークンを抑えられる

## 影響・見直し条件
- 実装が複雑になる。「画面に見える情報」と「モデルが見ている情報」がずれる瞬間がある（仕様として把握しておく）
- テンプレート規約 `ai-agent-context-engineering.md` の「選択・圧縮」を、この形で満たしている
