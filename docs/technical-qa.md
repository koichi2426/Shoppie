# Shoppie — 技術 Q&A

選定理由・設計判断・既知の制約を Q&A 形式でまとめたものです。実装の詳細は各ドキュメントを参照してください。

対象: [Shoppie](https://shoppie-agent.com) / [GitHub](https://github.com/koichi2426/Shoppie)

---

## プロダクト概要

### Q. Shoppie はどのようなプロダクトか？

**A.** 店員と話すように、音声やテキストで商品を探せるショッピングエージェント。曖昧な発話を LangGraph 上の LLM が解釈し、Yahoo・楽天・Amazon を横断検索して、短い返答と商品カードを返す。

### Q. 既存の EC 検索や一般的なチャットボットと何が違うか？

**A.** 検索ボックスやカテゴリドリルダウンではなく、会話そのものが検索インターフェース。技術的には「LLM に全部の商品 JSON を持たせない」三経路のデータ設計と、ツールスキーマによる検索条件の構造化が軸。

### Q. 設計上いちばん重視している点は？

**A.** 体験は「話すだけ」、裏側はコストとレイテンシを意識した分離。対話・ツール選択は LLM、商品表示は API フルデータ、LLM 文脈は最小フィールド、という役割分担。

### Q. 全体のリクエストの流れは？

**A.**

1. ユーザーが音声／テキスト → Next.js（Vercel）
2. ブラウザが FastAPI（Render）へ `POST /request-assistance`
3. LangGraph：Bedrock がツールを選び、Yahoo／楽天／Amazon を並列検索
4. MemorySaver に履歴、LLM には圧縮済みツール結果、画面にはフル商品
5. 短い日本語メッセージ + カードを返す

境界は「ユーザーを待たせる対話経路」「モデルに見せる情報量」「画面に出す情報量」で切っている。詳細は [アーキテクチャ概要](./architecture.md)。

## 技術選定

### Q. なぜバックエンドに FastAPI か？

**A.** API の言語より「エージェント・LLM・モール SDK を同じ言語圏で持つか」を優先した。

- LangGraph / LangChain / Bedrock SDK が Python 中心
- Pydantic で StructuredTool の引数契約を書ける
- 外部 API（モール・Bedrock）呼び出しが多いサービス向き
- 個人開発で速く回せる

| 比較案 | 採用しなかった理由 |
|--------|-------------------|
| Django | 管理画面は強いが、エージェント API＋ツール実行中心で重い |
| Nest / Node | フロントと同言語にできるが、LangGraph エコシステムと距離が遠い |
| Next.js だけで完結 | 秘密鍵やエージェントをブラウザ隣接に寄せたくなかった |

**トレードオフ**  
FE/BE が二言語・二デプロイになる。型は OpenAPI → `openapi-typescript` で同期している。

### Q. なぜフロントに Next.js か？

**A.** 「音声→検索→カード」の体験を最短で出すため。ランディング → 対話 UI → 商品グリッドを速く作りたかった。Vercel 親和性と App Router も決め手。

| 比較案 | 採用しなかった理由 |
|--------|-------------------|
| 素の React / Vite | SPA だけなら十分だが、ルーティング・本番配信・将来の SSR だと Next の方が楽 |
| Flutter 等のアプリ | ブラウザ音声（Web Speech API）で仮説検証したかったので Web 優先 |

**トレードオフ**  
フレームワークの厚み。ブラウザから FastAPI を直接叩く（BFF なし）ので CORS が必須。

### Q. 単発の LLM 呼び出しではなく、なぜ LangGraph か？

**A.** モデルの賢さに頼るより、ツール境界で推論を拘束するため。

曖昧な発話 → ツール選択 → モール API → 再応答、というループが必要。単発プロンプトだと「JSON を頑張って出させる」だけになり、検索の責務がプロンプトに全部乗る。

**グラフ構成**

- `llm_agent`：ツール選択 or 最終発話
- `tool`：Yahoo / 楽天 / Amazon（並列可）
- 空結果が連続したら打ち切り（無駄な再試行でトークンを燃やさない）

「検索クエリ文字列だけ出して、サーバーが固定 API を叩く」案は、拡張性とモール差への追従が弱く不採用。

**トレードオフ**  
グラフが増えるとデバッグが難しい。ノードは最小構成に留めている。

**実装の実態**  
意図抽出／構造化／要約の専用ノードに分かれているわけではない。現状は **LLM 1ノード + ツールノード + スキーマ拘束**。詳細は [LangGraph エージェント](./langgraph-agent.md)。

### Q. なぜ AWS Bedrock / Claude Haiku か？

**A.** 生成は短く、検索はツール、表示は UI、という分担で選定した。

- 日本語のツール選択と短い店員口調が欲しい
- 会話 UI なのでレイテンシとコストが大事 → Haiku + `max_tokens=256`
- 商品詳細はカード側に出す前提なので、長文生成は不要

より大きいモデルは精度が上がりやすいが、チャット1往復の体感と費用が悪化しやすい。複雑な条件交渉や長い説明は弱く、プロダクトとしては「短い案内＋カード」に寄せている。

### Q. なぜ DB や Redis を置かず MemorySaver だけか？

**A.** スケールより、まず対話が閉じる最小構成にした。

会話の永続化より「動く対話経路」を優先。チェックポイントは LangGraph の `MemorySaver`（プロセスメモリ）。

**既知の制約**

- Render 再起動で文脈消失
- Gunicorn **ワーカー1必須**（ワーカー跨ぎでメモリ非共有）
- アイドル 3 分でスレッド掃除（RAM 保護）
- Cookie の UUID は 7 日でも、サーバー側メモリは短命

最初から Redis / Postgres 永続化は正しいが、当時は運用コストが勝ちすぎた。将来は checkpointer を Redis 等へ移す余地がある。詳細は [セッション・デプロイ](./operations.md)。

### Q. なぜ音声に Web Speech API か？

**A.** 音声は体験の入り口。精度勝負は後段でもよく、まず摩擦を減らす側を取った。

追加課金なしのブラウザ STT で仮説検証できた。未対応ブラウザはテキスト入力にフォールバック。

Whisper / Deepgram などの常時サーバ STTは精度は上がるがコスト・パイプラインが増えるため、検証段階では不採用。

**後から変えた点**  
常時聞き取りは誤検知と負荷が重い → **タップで起動**。検索中はマイクを止める。

### Q. なぜマルチモール（Yahoo / 楽天 / Amazon）か？

**A.** 検索の幅はプロダクト価値、API 差はアダプタ層で吸収する、という判断。

単一モールだと比較価値が出にくく、横断検索が会話 UI の強みになる。

API ごとにパラメータ・認証・アフィリエイト条件が違う。Amazon は Associate 資格が足りないと Creators / PA-API が使えず、検索リンクフォールバックになる。

プロンプトに「使えるモールだけ使え」と明示しないと、無い API を嘘で失敗扱いする。可用性は設定駆動。詳細は [モール API 連携](./marketplace-apis.md)。

### Q. なぜクリーンアーキテクチャ風のレイヤー分けか？

**A.** LangGraph をユースケースの裏に閉じ込め、HTTP とドメインを守るため。

`adapter` / `usecase` / `domain` / `infrastructure` に分け、エージェント・モール・HTTP を混ぜない。

ファイルは増えるが、外部 API の差し替えやすさを優先した。詳細は [バックエンド](./backend.md)。

### Q. なぜ Vercel + Render + Cloudflare か？

**A.** FE とエージェントの障害域を分けつつ、各々の得意領域に寄せた。

| 層 | 選択 | 理由 |
|----|------|------|
| FE | Vercel | Next 親和性 |
| BE | Render + Docker | Gunicorn 1 worker で MemorySaver を守る |
| エッジ | Cloudflare | DNS / SSL / CDN |

フロントは Next API Routes を経由せず FastAPI を直接叩く。秘密は BE のみ。CORS で本番ドメインと localhost を許可。

CORS・二系統デプロイの運用はあるが、BFF より単純で、エージェント障害が FE デプロイと独立する。

## 設計の詳細

### Q. 中心になっている設計上の工夫は？

**A.** ユーザーに渡すデータと、モデルに渡すデータを分けたこと（三経路のデータ設計）。

モール API の生レスポンスをそのまま LLM に渡すと入力トークンがすぐ膨らむ、という制約から生まれた。

| 経路 | 中身 | 用途 |
|------|------|------|
| MemorySaver | ツール結果のフル JSON | 会話チェックポイント |
| Bedrock 入力（`messages_for_llm`） | 直近ツール結果・`title` / `price` 等の最小フィールド | 応答文生成 |
| API レスポンス | フル商品データ | 画面の商品カード |

全部 LLM に渡すとコスト・エラー・遅延が増える。件数だけ極端に間引くと比較体験が死ぬため、件数よりフィールドを削る方針にした。

三経路で実装は複雑になる。「画面に見える情報」と「モデルが見ている情報」が一致しない瞬間がある点は仕様として把握しておく必要がある。

### Q. 会話の文脈（セッション）はどう維持しているか？

**A.** セッションは「誰か」ではなく「同じブラウザ上の会話スレッド」のキー。秘密情報ではない。

1. Cookie `shoppie_context_id`（UUID）
2. API の `context_id`
3. LangGraph の `thread_id` → MemorySaver

ログインなしで続きの会話を可能にしている。フロントは履歴を持たず、毎回「今回の発話 + context_id」だけ送る。過去はバックエンド側。

認証なし・クライアント発行 ID のため、悪用耐性や横断端末での継続は弱い。

### Q. なぜ FE から直接 FastAPI を叩くか？（BFF なし）

**A.** パイプラインを単純にし、秘密をサーバー側に閉じるため。

Next API Routes を挟むと FE デプロイとエージェント障害が結びつきやすい。CORS allowlist でオリジンを制限している。

### Q. セキュリティはどうしているか？

**A.** まず秘密をブラウザに出さないことを優先。公開 API の悪用対策は今後の課題。

**実施済み**

- モール / Bedrock キーはサーバー環境変数のみ
- CORS allowlist
- 入力長のガード（発話・context_id 等）

**未整備／薄い点**

- 本格的なユーザー認証がない
- レート制限が薄い
- Cookie の context_id はスレッドキーでありセッション秘密ではない

## 制約・これまでの判断

### Q. いちばん手間がかかった技術的課題は？

**A.** 曖昧な口語をモール API の構造化パラメータ（価格帯・ソート等）に落とすことと、モールレスポンス肥大によるトークン上限の二段。

前者は StructuredTool + Pydantic で出力を拘束。後者は三経路のデータ分離で対応した。

### Q. トークン制限への対応はどのような位置づけか？

**A.** 生成 AI をプロダクトに載せるときの典型課題への設計応答。

商品 API の生データや長い履歴をそのまま LLM に入れると上限に触れる。履歴・ツール結果の圧縮と、生成上限（`max_tokens=256`）でコンテキスト量を抑えている。

### Q. 途中で変えた設計・UX は？

**A.**

- 常時音声 → タップ起動／検索中はマイク停止
- セッション ID の SSR 由来の乱れをクライアント側で整理
- 文脈は「前の発話は繋がるが、再起動や 3 分アイドルで消える」と割り切った

### Q. 今後入れたい／やり直すなら最初から入れるものは？

**A.** Redis checkpointer と、薄いレート制限層。説明・ドキュメントは実装（LLM 1ノード + ツール + スキーマ）に合わせる。

### Q. AI を実用アプリに載せるとき重視していることは？

**A.** モデル性能そのものより、推論プロセスをどう拘束するか。

Shoppie ではプロンプトの長さではなく、**ツールスキーマ**と**データ経路の分離**で行っている。

### Q. AgentHub など他プロダクトとの関係は？

**A.** 「重い LLM に全部任せず役割を分ける」という考え方は共通。Shoppie 側は対話は LLM、事実（商品）は外部 API、文脈コストは明示的に削る、という短い実証形態。

## 要約

| テーマ | 要点 |
|--------|------|
| プロダクト | 音声／テキストでモール横断検索するエージェント |
| 技術コア | 商品フルデータは画面、LLM には最小フィールド |
| LangGraph | ツール呼び出しループとして検索を構造化 |
| メモリ | DB なし MemorySaver。worker は1、文脈は短命 |
| 主な課題 | 曖昧発話の構造化と、モールレスポンスによるトークン肥大 |
| 現状の限界 | スケール・認証・レート制限はまだ薄い |
