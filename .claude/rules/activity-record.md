# 活動記録 — 試行の記録 Trials(必守)

一覧と書式: `docs/trials/README.md` / `docs/trials/0000-template.md`(ADR と同じく 1 問い 1 ファイル)
実験レポート: `docs/reports/README.md` / `docs/reports/0000-template.md`
仕組みは [koichi2426/AgentHub](https://github.com/koichi2426/AgentHub) の `docs/trials/` を移したもの([ADR-0013](../../docs/adr/0013-trials-record.md))。

## なぜ書くか

Shoppie で「何を試し、何がダメで、だから次はこうした」を、問いごとに残す。
ADR は選んだ構成を持つが、試行の回数と失敗の連なりは持たない。git 履歴は持っているが、問いごとにまとまっていない。

1. **何回やったか** — 問いごとの通し回数
2. **何がダメだったか** — 数値か観察した事実と、出典
3. **だから次はどうしたか** — 失敗から次の手への因果

## 書く調子(必守)

`docs/trials/`・`docs/reports/` は、第三者(採用の面接官など)が読む前提の**記録**として書く。

- 起きたこと・測ったこと・分かったことを、事実として淡々と書く。話すための下書き・想定問答などの「対策」は書かない
- 自分向けのメモや AI への指示を本文に書かない(「未記録」「要確認」「本人が埋める」「推測しない」「Claude が提案」など)
- 分からない欄は「—」にする。まだ測っていないことは「まだ測っていない」と書く
- 確認が要ることは、ファイルに書かずに作業の最後にオーナーへ聞く
- コミットメッセージ・PR の本文も同じ調子で書く(「指示で」「未記録のまま残す」などの内向きの言い方をしない)

## いつ書くか

**コードや設定を変えたら、同じ作業(同じ PR)の中で、該当する問いのファイルに 1 行足す。** 「あとで」は禁止。

- 書き忘れは Stop hook(`.claude/hooks/trials-record-check.sh`)が差し戻す。セッション開始以降に `fastapi/`・`nextjs/frontend/`・`docs/reports/` が変わったのに `docs/trials/` が変わっていなければ、1 回だけ停止を止める
- 既存の問いの続きなら、新しいファイルを作らずその問いの試行表に足す。答えが出たら「いまの結論」と状態を書き直す
- 成功だけでなく、**失敗・取り消し(revert)・途中でやめた試行も書く**。ここが本体
- 測ってみたら効かなかった、も 1 回の試行として数える
- 書かなくてよいもの: 誤字・整形だけの変更、依存の機械的な更新など、問いを持たない作業。そのときは Claude が理由を一言述べて終える

## 書き方

1. **まず既存の問いを探す。** `docs/trials/README.md` の一覧を読み、`grep -ril '<キーワード>' docs/trials/` で当たる。内容が少しでも被るなら新しいファイルは作らない
2. 被る問いがあれば、試行表の末尾に回を 1 つ増やして足す。やり直し・別の手での再挑戦も同じファイルの次の回
3. どの問いとも重ならないときだけ、テンプレートから `NNNN-<slug>.md` を新設し、README の表に 1 行足す。近い問いを「関連」に書き、なぜ別の問いなのかを「問いの背景」に 1 文で書く
4. ファイル冒頭の「試行回数」「状態」と、README の表の回数・状態を直す

各行の欄:

| 欄 | 書くこと |
|----|----------|
| 回 | 問いの中の通し番号 |
| 日付 | YYYY-MM-DD |
| やったこと | 1〜2 文 |
| 結果 | 数値は出典つき(レポート・ログ・計測)。数値が無ければ観察した事実。無ければ「—」 |
| 判定 | 成功/部分/失敗/破棄(やめた・戻した)/未判定 |
| 分かったこと | なぜダメだったか、または何が分かったか。分からなければ「—」 |
| 次 | 次に何をしたか(次の回へつながる) |
| 根拠 | コミットハッシュ、PR 番号、ADR 番号、レポートへのリンク |

## 実験レポートとの紐付け(必守)

レイテンシ・トークン数・費用・検索の当たり方など、測って判断した作業は `docs/reports/` にレポートを書く。

- **すべてのレポートは、どれかの問いの回に紐付ける。** 紐付け先の無いレポートは作らない。合う問いが無ければ先に問いを新設する
- レポート冒頭の「記録」に問いの番号と回を書く(例: T-0003 回8)
- 試行表の根拠の欄からレポートへリンクし、問いのファイルの「実験レポート」の表に日付順で足す
- `docs/reports/README.md` の一覧にも 1 行足す

## お気に入り(ファイル名に `KEY`)

`docs/trials/README.md` の先頭に、本人がお気に入りに登録した問いを並べる。登録した問いはファイル名の番号の後ろに `KEY` を付ける(例 `0002-KEY-…md`)。
**登録・解除は本人が決める。Claude は提案だけにとどめ、勝手に足し引きしない。** ファイル名を変えたら `grep -rl '<旧ファイル名>' docs` でリンクを直す。

## 起点(誰が決めたか)

起点は、オーナーに確かめられたときだけファイル冒頭に `- 起点:` として書く。確かめられないものは書かず、作業の最後にオーナーへ聞く。

- 実行者(本人の手作業/Cursor/Claude)は起点とは別。`Co-authored-by: Cursor` は実行者を示すだけで、起点の根拠にはならない

## 他の記録との関係

| 記録 | 持っているもの |
|------|----------------|
| `docs/trials/` | 問いごとの試行回数・失敗・次の手 |
| `docs/reports/` | 測って判断した実験の詳細(条件・数値・使ったデータ) |
| `docs/adr/` | 技術・構成の判断と、選ばなかった代替案 |
| git | 実際の変更 |

試行の記録は索引であって、詳細を二重に持たない。試行の結果として構成を選んだら、最後の回の根拠から ADR へリンクする。ADR の「関連」からは T 番号へリンクする。

## 禁止

- 既存の問いと被る内容で新しいファイルを作り、同じ話の回数を分散させること
- 失敗した試行を書かずに、成功だけを並べること
- 回数・理由を推測で埋めること(資料に現れた試行だけ数える)
- 起点を推測で書くこと
- 面接対策の下書き・想定問答を記録に混ぜること
- 既存の行を書き換えて経緯を消すこと(訂正は行を足すか、注記で示す)
